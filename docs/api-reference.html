§1

Visão geral

API REST em FastAPI, mais um WebSocket de notificações em tempo real. Recursos: conta e sessão, dados de mercado por ativo (ações, FIIs, ETFs, BDRs e cripto), watchlist, alertas de preço, portfólio, análise por IA e notificações. Tudo em JSON, sob o prefixo abaixo — exceto o health check.

Base URL (dev)
http://localhost:8000
Prefixo dos recursos
/api/v1
Health check
GET /health (sem prefixo)
Autenticação
Authorization: Bearer <access_token>
Access token
30 min (padrão)
Refresh token
30 dias, rotativo
WebSocket
ws://localhost:8000/api/v1/notificacoes/ws
Content-Type
application/json
Valores decimais chegam como string

Todo campo monetário ou numérico com casas decimais (preco, valor_alvo, volume, quantidade, percentuais etc.) é serializado como string: "preco": "38.42", não 38.42. Isso preserva a precisão — convertam no client com uma lib decimal (ou Number() só para exibição). Inteiros puros (expires_in, total_ocorrencias) continuam números.

CORS

O backend libera as origens listadas na variável CORS_ORIGENS (padrão: http://localhost:5173). O front web precisa avisar qual origem usa em staging/produção para entrar na lista. Mobile e desktop nativos não são afetados por CORS.

§2

Erros & formatos

Dois formatos de erro convivem na API — tratem os dois no client.

Erro de regra de negócio (a maioria dos 4xx/5xx)
{
  "detail": "Ativo nao encontrado"
}
Erro de validação de payload (422, gerado pelo Pydantic)
{
  "detail": [
    {
      "loc": ["body", "valor_alvo"],
      "msg": "Input should be greater than 0",
      "type": "greater_than"
    }
  ]
}

Regra prática: se detail é string, mostre a mensagem; se é array, é erro de formulário.

Formatos de campo
TipoFormato
decimalstring, ex: "38.42" (ver §1)
datetimeISO 8601 em UTC, ex: "2026-09-15T13:00:00Z"
date"YYYY-MM-DD" (só em operações do portfólio)
idUUID v4 em string
Correlation id (X-Request-ID)

Toda resposta HTTP traz o header X-Request-ID. O client pode enviar o próprio (até 64 caracteres: letras, números, ., _, -) para rastrear a requisição; senão o backend gera um. Ao reportar um bug, mandem esse id junto — é ele que localiza a requisição nos logs do servidor.

§3

Autenticação

Cadastro, login e refresh retornam o mesmo TokenResponse: um access token JWT curto (vai no header Authorization das rotas 🔒 autenticado) e um refresh token opaco e longo, usado só para obter um novo par.

Regras do refresh — leiam antes de implementar
  • Rotação: cada /auth/refresh devolve um refresh token novo e invalida o anterior. Sempre substitua o refresh salvo pelo que veio na resposta.
  • Serializem o refresh: só uma chamada de refresh por vez por sessão. Se duas requisições paralelas tomarem 401 e ambas tentarem renovar com o mesmo refresh token, a segunda é tratada como reuso de token roubado e a sessão inteira é revogada (todos os tokens daquele login) — o usuário cai para o login. Usem uma fila/mutex: a primeira renova, as demais esperam e reaproveitam o novo access token.
  • Quando renovar: ao receber 401 em rota autenticada (e repetir a requisição uma vez), ou proativamente um pouco antes de expires_in segundos.
  • Refresh falhou (401): sessão acabou — limpe os tokens e mande para o login.
  • Armazenamento: o refresh token vale 30 dias; guardem em storage seguro (Keychain/Keystore no mobile). No web, evitem localStorage se possível.
TokenResponse
{
  "access_token": "eyJhbGciOi...",
  "refresh_token": "Xq3v9...k2",
  "token_type": "bearer",
  "expires_in": 1800
}

expires_in é a validade do access token em segundos.

POST /api/v1/auth/refresh 🔓 público

Troca um refresh token válido por um par novo (access + refresh). Não envie o header Authorization — o access pode já estar expirado.

Body

  "refresh_token": "Xq3v9...k2"
}

Erros

POST /api/v1/auth/logout 🔓 público

Revoga a sessão do refresh token informado (só aquele login — outros dispositivos continuam logados). Idempotente: token desconhecido ou já revogado também responde 204. O access token atual continua válido até expirar (≤ 30 min), então descartem ele no client e fechem o WebSocket.

Body
{
  "refresh_token": "Xq3v9...k2"
}
204 No Content
§4

Ativos

Busca de ativos e dados de mercado (cotação, histórico, indicadores técnicos e sinais). Todas as rotas exigem 🔒 autenticado. Renda variável vem da brapi.dev; cripto vem da Binance, sempre cotada em BRL.

Cripto

Criptomoedas usam o código do ativo como ticker (BTC, ETH, SOL…), com tipo: "CRIPTO" e moeda: "BRL" — preço, histórico e alertas são em reais. Só entram moedas que têm par BRL ativo na Binance. Mercado 24/7: a cotação de cripto se mexe no fim de semana.

§7

Portfólio

Carteira montada a partir das operações de compra e venda registradas pelo usuário. Posições, preço médio e lucro são recalculados a partir das operações. Todas as rotas exigem 🔒 autenticado.

Percentuais do portfólio são frações

Em /portfolio/rentabilidade, /portfolio/benchmark e /portfolio/distribuicao os percentuais vêm como fração: "0.1234" = 12,34%. Multipliquem por 100 para exibir. (Diferente de /cotacao e do backtest, que já vêm em pontos percentuais.)

§8

Análise por IA

Texto gerado por LLM a partir de cotação, indicadores e sinais. Ambas as rotas exigem 🔒 autenticado e devolvem aviso_legal — exibam esse texto junto da resposta. A IA pode estar desligada no ambiente: nesse caso as rotas respondem 503 "Provedor de IA indisponivel" e o client deve esconder/desabilitar a funcionalidade.

GET /api/v1/ativos/{ativo_id}/analise 🔒 autenticado

Análise do ativo. Se os dados do ativo não mudaram desde a última análise, devolve a mesma (rápido, em_cache: true). Se mudaram, gera uma nova — pode levar vários segundos; mostrem loading.

200 OK
{
  "ativo_id": "3fa8...",
  "texto": "PETR4 fechou em alta de 1,5%...",
  "gerado_em": "2026-09-15T13:00:00Z",
  "modelo": "gemini-3.5-flash",
  "em_cache": false,
  "desatualizada": false,
  "aviso_legal": "Análise gerada por IA. Não constitui recomendação de investimento."
}
Campos de estado
CampoSignificado
em_cachetrue quando é uma análise já salva (não foi gerada agora).
desatualizadatrue quando o provedor de IA falhou e o backend devolveu a última análise disponível, que não reflete os dados mais recentes. Mostrem um aviso tipo "análise de <gerado_em>, pode estar desatualizada". Sempre vem com em_cache: true.
Erros
404"Ativo nao encontrado"
422"Dados insuficientes para gerar a analise" — ativo sem histórico/indicadores ainda
502"Resposta da IA bloqueada pelo guardrail"
503"Provedor de IA indisponivel" (inclui IA desligada) ou "Cota do provedor de IA excedida" (pode ter Retry-After, em segundos). Só ocorre se não houver análise anterior para devolver como desatualizada.
POST /api/v1/chat 🔒 autenticado

Chat sobre a carteira do usuário (a IA consulta posições, rentabilidade, distribuição, operações e benchmark). O backend não guarda conversa: o client manda o histórico inteiro a cada chamada, terminando com a mensagem do usuário, e acrescenta a resposta como "assistente" antes da próxima.

Body
{
  "mensagens": [

WS /api/v1/notificacoes/ws 🔒 via mensagem

Canal em tempo real. Use ws:// em dev e wss:// em produção. O token não vai na URL nem em header: a primeira mensagem depois de conectar é a autenticação. Todas as mensagens são JSON em texto com um campo tipo.

Mensagens
DireçãotipoPayload
client → serverautenticar{ "tipo": "autenticar", "token": "<access_token>" }
server → clientautenticado{ "tipo": "autenticado" } — confirmação
server → clientnotificacao{ "tipo": "notificacao", "notificacao": Notificacao }
server → clientping{ "tipo": "ping" } a cada 30 s — não precisa responder; serve para detectar conexão morta
Fluxo
  1. Conectar e, em até 10 s, enviar autenticar com o access token.
  2. Esperar autenticado. A partir daí chegam notificacao e ping.
  3. Antes do access token expirar, renovar via /auth/refresh e mandar autenticar de novo na mesma conexão com o token novo (do mesmo usuário). O server responde autenticado e estende a sessão. Se não fizer isso, o server fecha com 4401 quando o token expira.
  4. Ao receber uma notificacao, inserir na lista local / mostrar toast. Não é preciso confirmar recebimento.
Códigos de fechamento
CódigoMotivoO que o client faz
4401Não autenticou em 10 s, token inválido/expirado, re-autenticação com token de outro usuário, ou access token expirou sem renovaçãoRenovar o access token (refresh) e reconectar. Se o refresh falhar, ir para o login.
1011Erro interno no servidorReconectar com backoff.
outrosQueda de rede, deploy, proxyReconectar com backoff exponencial (ex: 1 s, 2 s, 4 s… até 30 s).
Ao reconectar, sincronize pelo REST

O WebSocket não reenvia o que chegou enquanto o client estava desconectado. Depois de cada (re)conexão autenticada, chamem GET /api/v1/notificacoes?apenas_nao_lidas=true e mesclem com o que já está na tela (deduplicando por id). Façam o mesmo quando o app volta do background.

Exemplo (JS)
const ws = new WebSocket("wss://api.exemplo.com/api/v1/notificacoes/ws");
ws.onopen = () => ws.send(JSON.stringify({ tipo: "autenticar", token: accessToken }));
ws.onmessage = (ev) => {
  const msg = JSON.parse(ev.data);
  if (msg.tipo === "autenticado") sincronizarNaoLidas();
  if (msg.tipo === "notificacao") adicionarNotificacao(msg.notificacao);
};
ws.onclose = (ev) => {
  if (ev.code === 4401) renovarTokenEReconectar();
  else reconectarComBackoff();
};

Rodando local

Para apontar o app/web para o backend local:

docker compose up

# sobe API em http://localhost:8000, Postgres e Redis
# migrations do Alembic aplicadas automaticamente

Sem BRAPI_API_KEY, cotação e histórico de renda variável só respondem para PETR4, MGLU3, VALE3, ITUB4. Cripto (Binance) funciona sem chave. A IA fica desligada por padrão (AI_HABILITADA=false) — as rotas de IA respondem 503 até alguém configurar GEMINI_API_KEY. Para testar o web local, a origem precisa estar em CORS_ORIGENS.
